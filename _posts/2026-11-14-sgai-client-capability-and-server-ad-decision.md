在基于 **HLS Interstitials（`#EXT-X-DATERANGE`）** 构建 **SGAI（Server-Guided Ad Insertion，服务端引导广告插入）** 系统时，一个核心的架构问题是：**“到底该由谁来决定某个广告位播放什么形态的广告？”**

比如，在直播或点播场景中，我们希望在合适的时间点（例如比赛暂停、回放或非关键片段）尝试插入不打断主画面的 **L 型缩屏广告（Squeezeback / L-Bar）** 或 **可点击交互广告**；而在其他时间点，或者遇到不支持复杂渲染的播放器时，则退回到传统的全屏线性广告。

如果处理不好，很容易把“广告位意图”和“播放器能力”混在一起，导致两端逻辑越来越重。经过实践与思考，一种更清晰、也更贴近工业界主流做法的模式是：

> **播放器不做思考、不做协商，只在 `X-ASSET-LIST` 请求中如实声明自身能力；由后端广告决策服务（ADS）结合广告位上下文与客户端能力做出最终决定。**

---

## 为什么“清单硬编码”和“客户端协商”都会带来麻烦？

### 1. 在播放清单（Manifest）里硬编码广告形态
如果服务端生成的 `#EXT-X-DATERANGE` 直接把格式写死，例如：

```m3u8
X-ASSET-LIST="/api/ads?type=squeezeback"
```

而后端据此无条件返回一段 L 型缩屏视频，那么一旦遇到不支持缩屏合成的客户端（例如原生 Safari / AVPlayer 的默认 HLS Interstitials 行为，或未做定制的基础版 `hls.js`），播放器就会把这段 L 型广告视频**全屏播放**。观众看到的将是画面中占 75% 面积的一块黑色留白——原本应该放主视频的位置变成了一片黑。

### 2. 在客户端做条件判断与协商
另一种常见误区是：Manifest 里放一些自定义属性（如 `X-AD-TYPE="continue"`），然后让客户端在到达每个广告位时先解析这些属性，再决定“这一次要不要向后端请求 squeezeback”、“要拼哪些查询参数”。

这样做的代价是**客户端逻辑快速膨胀**。而且一旦业务要覆盖 Web、iOS、Android、各种智能电视（CTV），同样的条件分支和协商逻辑就必须在所有端上各写一遍、各测一遍，维护成本极高。

## 更优雅的三层职责划分

要彻底解耦，可以把一次广告插播拆成三个互不越界的职责层：

```text
+-------------------+         +-----------------------+         +------------------+
|   HLS Manifest    |         |     Player (Client)   |         |    Ad Server     |
|  (广告位客观描述)   |         |     (固定能力声明)     |         |   (唯一决策大脑)  |
+-------------------+         +-----------------------+         +------------------+
         |                               |                               |
         | X-ASSET-LIST 携带             |                               |
         | slot, duration, playback 等   |                               |
         |------------------------------>|                               |
         |                               | GET X-ASSET-LIST              |
         |                               |   + clickable=1&squeezeback=1 |
         |                               |------------------------------>|
         |                               |                               | 综合广告位属性、
         |                               |                               | 客户端能力与广告库存
         |                               |  返回 ASSETS[0] 及渲染元数据   |
         |                               |<------------------------------|
         |                               | 按返回的 LAYOUT / BUTTON 渲染  |
         |                               |                               |
```

### 1. 中立的 Manifest：只描述“广告机会”
播放清单里的 `#EXT-X-DATERANGE` 只负责描述广告位（Slot）本身的客观约束，不涉及任何 UI 或渲染形态，并且把这些约束直接放进 `X-ASSET-LIST` 的 URL 参数中，例如：

- `slot`：广告位标识
- `duration`：可用时长（如 `5.0` 或 `10.0`）
- `playback`：主内容在此广告位期间必须暂停（`block`），还是允许继续播放（`continue`）

这样做还有一个隐形好处：**即使是不认识任何自定义 `X-*` 扩展属性的标准播放器，也会把 `X-ASSET-LIST` 原封不动地转发给后端**，从而把完整的广告位上下文带过去。

### 2. 无状态的客户端：只声明“我能做什么”
播放器不需要理解什么叫“广告协商”。当触发某个广告位时，它只需要：
1. 原样取出 `X-ASSET-LIST` URL；
2. **无条件追加**自己固定支持的能力参数（例如支持可点击按钮 `clickable=1`、支持 L 型缩屏 `squeezeback=1`）；
3. 发起请求，拿到结果后**完全服从后端返回的布局与交互描述**——返回 `l-squeezeback` 就缩屏并保持主视频播放，否则就全屏并暂停主视频；返回了按钮元数据就渲染按钮。

如果一个老旧设备或原生播放器完全不追加这些能力参数，后端自然会给它下发最基础的全屏广告，**实现零成本的优雅降级**。

### 3. 唯一的决策点：后端广告决策服务（ADS）
所有的匹配规则都收敛在后端一处：
- **广告位允许 `continue` + 客户端支持 `squeezeback`**：可以下发 L 型缩屏广告素材及对应的布局指令；
- **广告位要求 `block`，或客户端未声明 `squeezeback`**：自动降级为标准全屏线性广告；
- **客户端声明了 `clickable`**：附带交互按钮元数据；否则省略。

未来如果要新增一种广告形态（例如画中画、倒计时角标或新的交互卡片），只需要在后端决策表里增加规则，并在支持该形态的播放器上多上报一个能力标记即可，**不需要改动播放清单格式，也不需要在客户端写复杂的分流逻辑**。

## 工业界的真实实践对照

这种“清单描述机会 + 端侧声明能力 + 服务端统一决策”的思路，实际上与目前主流流媒体广告生态的工业实践高度一致：

### 1. Apple HLS Interstitials 规范
在 Apple 的 HLS Interstitials 体系中，主播放清单对所有观众保持一致，仅通过 `#EXT-X-DATERANGE` 和 `X-ASSET-LIST` 声明插播时机。无论是 iOS / tvOS 原生的 `AVPlayerInterstitialEventController`，还是 Web 端的 `hls.js` / `Shaka Player`，都是在到达插播点前动态请求 `X-ASSET-LIST` 获取 JSON 列表。原生或基础播放器只消费标准的 `ASSETS` 媒体列表实现安全降级；定制客户端则可以在请求上附带环境与能力参数，让服务端返回更丰富的体验。

### 2. 云厂商的 SGAI 方案（Google DAI 与 AWS Elemental MediaTailor）
在高并发直播场景中，**Google Dynamic Ad Insertion (DAI)** 和 **AWS Elemental MediaTailor** 都已经引入了对 SGAI 模式的支持（基于 HLS Interstitials 或 DASH 对应机制）。服务端不再把单一的广告视频硬编码拼接进所有人的流里，而是由清单给出插播信令，再由决策层在请求时结合设备与客户端上下文决定具体返回的资产和呈现方式，从而兼顾 CDN 缓存效率与终端体验差异化。

### 3. 直播体育中的 L-Bar / Squeezeback 变现
在体育直播（如足球、篮球、赛车）中，传统全屏插播很容易打断关键赛况导致观众流失。**FloSports** 等平台以及 **Bitmovin**、**StreamLayer**、**castLabs PRESTOplay** 等播放器/交互 SDK 厂商在实践中广泛采用了 SGAI + L-Bar 模式：
- 在比赛暂停、裁判回看或慢动作回放等间隙，上游通过 SCTE-35 等信令标记出“可不断流（continue）”的广告机会；
- 具备双路解码或画面缩放能力的新款 CTV 与 Web 端会上报相应能力，触发主画面缩屏并展示带赞助商视频、二维码或 CTA 的 L 型栏；
- 而解码能力受限的老旧电视盒子由于未上报该能力，会自动回退到普通广告或跳过，不会出现画面撕裂或黑屏。
- **IAB Tech Lab** 也已将 Squeezeback、L-Bar 等非侵入式 CTV 广告格式纳入标准，并在 OpenRTB 竞价请求中定义了对应的能力信号，让程序化买方可以直接针对支持该形态的终端出价。

### 4. IAB VAST 4.x 与 SIMID / OMID 的能力过滤
在传统的 VAST（Video Ad Serving Template）生态中，**Google Ad Manager**、**FreeWheel**、**Kevel** 等主流广告服务器同样遵循“客户端只报能力，ADS 负责过滤”的原则：
- 播放器在每次广告请求中固定带上自己支持的交互规范（如 **SIMID**——用于替代早期 VPAID 的安全交互层）和可见性监测规范（如 **OMID / OM SDK** 版本）；
- 如果某个广告创意强制依赖 SIMID 交互脚本，但发起请求的 CTV 设备并未声明支持运行 HTML/JS 交互层，广告服务器就会在决策阶段直接过滤掉该创意，绝不会把不兼容的广告下发给客户端。

## 小结

把“判断逻辑”从客户端拿走，表面上看只是少写了几行 `if/else`，本质上是在流媒体广告链路中确立了清晰的边界：
- **Manifest** 只说“这里有个什么样的机会”；
- **Player** 只说“我具备哪些渲染能力”；
- **Server** 负责“把合适的广告匹配给合适的终端”。

这既让客户端保持轻量、无状态、易跨平台维护，也让整个系统具备了工业级的扩展性与安全降级能力。
